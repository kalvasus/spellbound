# 협업 규칙

SPELLBOUND 팀이 15주 동안 지킬 최소 규칙입니다.
게임 개발 협업이 처음인 사람 기준으로 썼습니다. 읽는 데 5분, 지키는 데 부담 없게 만들었습니다.

---

## 1. 누가 어떤 파일을 소유하는가

이 프로젝트에서 Git 충돌이 거의 나지 않는 이유는 **파일 주인이 정해져 있기 때문**입니다.
남의 파일을 고쳐야 하면 직접 고치지 말고 주인에게 요청하세요.

| 파일 · 폴더 | 주인 | 설명 |
|---|---|---|
| `src/engine.js`, `src/rogue.js`, `build.py` | 정민석 | 게임 로직·저장·로그·빌드 |
| `src/engine.css`, `src/engine.body.html`, `src/art.js`, `src/assets/` | 강수정 | 화면·아이콘·사운드 에셋 |
| `src/data_en.js`, `src/data_es.js`, `analysis/` | 박종효 | 단어 데이터·분석 스크립트 |
| `docs/` | 우정민 | 기획·실험 문서 |
| `.github/`, `CONTRIBUTING.md`, 일정표 | 이희건 | 저장소 운영·일정 |

### 유일한 공유 지점: `engine.body.html`

강수정이 화면 구조를, 정민석이 그 화면을 조작하는 코드를 씁니다.
둘을 잇는 것이 **요소의 `id`**(`word-input`, `boss-emoji`, `pot-bar` 등)입니다.

> **id는 두 사람의 계약입니다. 바꾸기 전에 반드시 상대에게 알리세요.**
> 말없이 바꾸면 화면은 멀쩡한데 게임이 동작하지 않고, 원인을 찾는 데 반나절이 갑니다.

## 2. 브랜치와 병합

복잡한 전략은 쓰지 않습니다. 아래가 전부입니다.

```
main  ←  각자 작업 브랜치에서 PR
```

1. 작업 시작 전에 최신 상태를 받는다
   ```bash
   git checkout main
   git pull
   ```
2. 내 브랜치를 만든다 — `이름/작업내용`
   ```bash
   git checkout -b minseok/save-progress
   ```
3. 작업하고 커밋한다 (하루에 한 번 이상)
   ```bash
   git add .
   git commit -m "저장 기능: localStorage 읽기/쓰기 구현"
   git push -u origin minseok/save-progress
   ```
4. GitHub에서 Pull Request를 연다
5. **회귀 테스트가 통과해야 병합된다.** 병합 승인은 이희건.

### 커밋 메시지

거창한 규칙 없이, **무엇을 왜 바꿨는지** 한 줄이면 됩니다.

```
좋음   저장 기능: 탭을 닫아도 숙련도가 유지되도록 localStorage 연결
좋음   맵 아이콘: 노드 타일이 작아 식별이 어려워 26px → 30px
나쁨   수정
나쁨   ㅇㅇ
나쁨   asdf
```

커밋 이력은 **학기말 개인 기여 증빙**으로 그대로 쓰입니다.
마지막 주에 몰아서 올리면 아무 일도 안 한 것처럼 보입니다.

---

## 3. 절대 커밋하면 안 되는 것

| 대상 | 이유 |
|---|---|
| `dist/` (빌드 결과물) | 빌드할 때마다 전체가 바뀌어 **모든 병합에서 충돌**난다 |
| `node_modules/` | 용량이 크고 각자 설치하면 된다 |
| 실험 참가자 데이터 | 개인정보. 공유 드라이브로만 주고받는다 |
| DAW·PSD 원본 파일 | 용량이 크고 병합이 불가능하다 |

`.gitignore`에 이미 걸려 있습니다. 지우지 마세요.

### 바이너리 파일 규칙

mp3, png 같은 파일은 **Git이 병합하지 못합니다.** 두 사람이 같은 파일을 고치면
한쪽 작업이 그냥 사라집니다. 그래서 `assets/` 폴더는 강수정 한 사람만 건드립니다.

---

## 4. 에셋을 추가하는 방법

코드를 고칠 필요 없이 **파일만 떨어뜨리면** 빌드가 알아서 집어갑니다.

```
assets/
  icons/   *.svg    → 파일명이 그대로 아이콘 키가 된다 (wolf.svg → icon("wolf"))
  sfx/     *.mp3    → 짧은 효과음. 빌드 시 HTML 안에 인라인된다
  bgm/     *.mp3    → 배경음악. 용량이 커서 외부 파일로 배포된다
```

- SVG는 Figma·일러스트레이터에서 그대로 내보내면 됩니다.
- 효과음은 **한 개 50KB 이하**로 유지하세요. 인라인되기 때문에 그대로 빌드 용량이 됩니다.
- BGM은 용량 제한이 덜하지만, 곡당 3MB를 넘기지 마세요.

> **W11부터 W13까지(실험 기간)는 오디오를 바꾸지 않습니다.**
> 참가자마다 다른 소리를 들으면 실험의 통제 조건이 깨집니다.

## 5. 주간 리듬

| 언제 | 무엇 |
|---|---|
| 매일 | 작업했으면 커밋하고 push |
| 주 1회 (30분) | 정기 회의 — 지난주 완료 / 이번 주 계획 / 막힌 것 |
| 주 1회 | 각자 브랜치를 `main`에 병합. **미루지 않는다** |
| 회의 후 | 일정표의 상태 열 갱신 (본인 몫은 본인이) |

### 통합을 미루면 생기는 일

첫 협업에서 가장 흔한 실패는 **각자 두 달 작업하다가 마지막에 합치는 것**입니다.
그때는 충돌이 수백 개가 되고 누구 코드가 맞는지 아무도 모릅니다.

**작게, 자주 합치세요.** 매주 병합하면 충돌은 매번 몇 줄에 그칩니다.

---

## 6. 막혔을 때

- **충돌이 났다** → 혼자 해결하려다 망가뜨리지 말고 채널에 스크린샷을 올리세요. 되돌리는 건 항상 가능합니다.
- **"내 컴퓨터에선 되는데"** → CI가 기준입니다. CI에서 실패하면 실패한 겁니다.
- **2주 연속 같은 곳에서 막혔다** → 회의에서 말하세요. 역할을 재배치하는 게 낫습니다.

## 7. 개발 환경

```bash
# 최초 1회
pip install playwright
playwright install chromium

# 빌드 — dist/index.html 이 만들어진다
python3 build.py

# 소스 검사만 (단어 중복·결측 확인)
python3 build.py --check

# 테스트 (4개 스위트 전부 통과해야 병합 가능)
python3 tests/test_core.py
python3 tests/test_rogue.py
python3 tests/test_learn.py
python3 tests/test_psych.py
```
